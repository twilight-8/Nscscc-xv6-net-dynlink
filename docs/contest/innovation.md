# 创新性分析

本文按“创新内容 / 实现手段 / 创新价值”三段式提炼本项目的编号创新点。功能与主要稳定性路径对应 `src/` 中的实际代码和自动化回归；难以确定触发的并发发布协议以锁序/内存序审查补充，历史性能记录单独标明版本边界。

## 创新点 1：薄 VFS 分发层（406 行实现三文件系统共存）

- **创新内容**：为 xv6-riscv rev5 增加虚拟文件系统能力，同时支持 xv6、ext2、fat32 三种文件系统挂载共存与跨系统互操作。
- **实现手段**：`vfs.c` + `vfs.h` 定义 `inode_ops`/`fs_ops` 操作表、拓扑修改专用可睡眠操作锁与四态挂载表；操作锁串行化完整 `mount/umount`，四态负责发布、失败回滚、unlink 可见性和卸载隔离，短期 reader pin 与既有 `inode.ref` 分别解决路径取引用窗口和长期 busy 判断。`struct inode` 仅增加 `fstype/mnt/ops` 三个字段；原生 xv6 文件系统作为默认后端接入同一接口。最终代码规模以源码冻结后重新生成的 diff 统计为准，新增后端与平台代码均隔离在独立文件中。
- **创新价值**：以教学级的代码体量完成多文件系统统一接入，证明 VFS抽象可以是“薄”的；区别于参照项目动辄数千行的 VFS 子系统，本实现每一行可在课堂上讲清（详见 `comparison.md`）。

## 创新点 2：单一 virtio 盘上的三文件系统镜像布局

- **创新内容**：xv6、ext2、fat32 三个文件系统共存于同一块虚拟磁盘，通过块设备偏移划分区域，互不干扰。
- **实现手段**：`param.h` 以常量定义各区段边界（FSSIZE/EXT2SIZE/ FAT32START），`virtio_disk.c` 按逻辑设备号（1/2/3）将读写偏移映射到对应区段；镜像构建由 mkfs/mkfs.ext2/mkfat32 串联生成。
- **创新价值**：不引入多磁盘、不修改 QEMU 配置即完成多文件系统并存，布局常量与构建依赖闭环（改区段大小自动触发镜像重建），是“小而完整”的系统设计范例。

## 创新点 3：双平台对称的薄 HAL 与中断路由知识收敛

- **创新内容**：RISC-V 与 LoongArch64 两个平台共用全部上层代码，中断与磁盘访问经统一 HAL 接口分发。
- **实现手段**：RISC-V `hal.c`（46 行）与 LoongArch `hal.c`（52 行）提供 `hal_intr_init`/`hal_irq_claim`/`hal_irq_complete`/`hal_disk_*` 薄接口；LoongArch 侧把 EXTIOI 位掩码语义与 LS7A APIC 电平/边沿、路由差异（virtio 电平触发需 APIC 清除、UART 边沿触发无需）全部收敛进 `arch/loongarch/hal.c`，`trap.c` 不再直触中断控制器，两端结构对称。
- **创新价值**：证明 HAL 可以极薄且双端对称；平台差异被限制在单一文件内，为后续接入第三平台提供清晰范式。

## 创新点 4：丢失中断的机制级兜底（virtio 看门狗）

- **创新内容**：针对 LoongArch 传统 INTx 链会吞掉“确认窗口内到达的完成中断”这一已实证缺陷，提出并实现“中断是快速通道、看门狗是正确性通道”的双层结构。
- **实现手段**：devintr 的 virtio 分支在确认后循环重查 used 环；`virtio_disk_watchdog()` 挂在定时器中断路径（不经过外部中断链），每 tick 检查并清理未处理的完成项；锁空闲检查避免自死锁。
- **创新价值**：把一类硬件信号竞态导致的死锁从机制上降为最多一个tick 的延迟，是操作系统容错设计思想在教学内核上的具体落地（案例全程记录于 `problems.md` P5）。

## 创新点 5：缺陷驱动的测试工程体系

- **创新内容**：为教学操作系统构建覆盖“功能、语义、并发、持久、性能”的自动化测试与证据体系。
- **实现手段**：11 个测试点 × 2 个架构统一三件套（命令/断言/说明）；QEMU 驱动支持 `--cpus`、首条与后续命令提示符稳定等待、精确次数与负断言；新增生命周期时间线、双后端 1 MiB 多轮重挂载和 2048 次 worker 迭代的挂载风暴；`make verify-all` 一键复现功能回归，`e2fsck` 独立校验镜像一致性。
- **创新价值**：主要功能与稳定性结果可由评审通过统一命令复现；对冷 inode 和 `MOUNTING` 这类难以确定命中的并发窗口，则把自动化防回归与锁序/内存序审查结合，形成可核查且不过度宣称的证据链。runner 的等待机制本身也由实测缺陷驱动演进（记录于 `problems.md` P8）。
