# 研发过程中遇到的问题和解决方法

本文按“现象与取证 → 根因分析 → 修复方法 → 验证方式”的结构，记录本项目研发过程中发现并解决的主要技术问题。每个案例均可在提交历史的对应提交与 `tests/evidence/` 的日志中复核。

## P1. 官方评测流程在 /tests 下全部 exec 失败

- **现象与取证**：按官方参考流程 `cd tests; cat cmds.sh | sh` 演练时，`ls`、`cat`、`test1`、`test2` 全部返回 `exec failed`。探针日志显示命令在 `/tests` 工作目录下解析，找不到可执行文件。
- **根因**：xv6 的 `exec` 只按调用者给出的路径解析，裸命令名只查当前目录；官方流程却要求在 `/tests` 里运行安装在根目录的程序。
- **修复**：`kexec` 中对不含 `/` 的裸命令名增加根目录回退查找（`namei` 失败后用 `/` 前缀重试一次），约 16 行。
- **验证**：官方流程双架构输出与上游参考输出逐字节一致；`usertests`全量回归通过。

## P2. 打开中的文件被 unlink 后语义错误（B2）

- **现象与取证**：代码审查发现 ext2/fat32 的 `unlink` 在链接数归零时立即释放 inode/簇链，与 xv6 原生语义（最后一次 close 才释放）不一致；仍持有 fd 的进程随后读写会碰到已释放资源。
- **根因**：`iput()` 对非 xv6 后端缺少 `ref==1 && nlink==0` 的延迟释放分支，释放被错误地放在 unlink 路径上。
- **修复**：unlink 只减 `nlink` 并同步；释放移入 `iput()` 的对应分支，经各后端 `itrunc` 钩子完成（ext2 释放块与 inode，fat32 释放整条簇链）。
- **验证**：新增 `unlinkopen` 回归用例（双 fd 打开→unlink→读校验→关闭后确认不复活），并入 `semantics` 测试点双架构通过。

## P3. 挂载点可被删除、根文件系统可重复挂载（B3/B5）

- **现象与取证**：探针实证 `rm /mnt` 成功，挂载关系即刻失效，已挂载文件系统中的数据不可读；`mount xv6 /xv` 静默成功并呈现损坏目录视图。
- **根因**：三条 unlink 路径（xv6/ext2/fat32）均未检查目标是否为挂载点；`vfs_mount` 未拒绝已挂载的 xv6 根。
- **修复**：unlink 路径对 `vfs_mountpoint(ip) != 0` 返回失败；`vfs_mount` 拒绝 fstype 为 xv6 的请求。
- **验证**：修复后探针复测，双架构行为一致（删除被拒、挂载被拒、数据可达）。

## P4. ext2 大文件支持的连锁缺陷（双重间接 + dinode 拷贝越界）

- **现象与取证**：实现双重间接块（将 `struct inode` 的 `addrs` 扩一个槽位）后，全量回归在 `fourfiles` 处 panic：`ilock: no type`。
- **根因**：`iupdate`/`ilock` 用 `sizeof(ip->addrs)` 与磁盘 dinode 互拷，内存槽位扩容后多拷 4 字节，`iupdate` 会覆写相邻 dinode 的 `type`字段；并发创建文件时相邻 inode 被清零。
- **修复**：拷贝上界改为 `sizeof(dip->addrs)`，并确立“内存扩展槽位绝不外溢到磁盘布局”的约束，写入 `docs/design.md`。
- **验证**：修复后 `usertests` 完整版双架构通过；`e2fsck -fn` 对 ext2镜像五阶段校验零错误。

## P5. LoongArch 磁盘完成中断丢失导致系统挂死

- **现象与取证**：完整版 `usertests` 在 LoongArch 的 `manywrites` 上确定性挂死，无任何输出。gdb 取证：设备已投递完成项（`used->idx=652`）而客户机从未处理（`used_idx=650`），全部进程睡眠、CPU 空转。二分测试确认该缺陷早于决赛改动即存在（初始移植遗留）。
- **根因**：传统 INTx 信号链上，一次完成在中断确认窗口内到达时可能被APIC/EXTIOI 链吞没且不再产生新中断；等待磁盘完成的进程从此无人唤醒。
- **修复**：双层防护——devintr 的 virtio 分支确认后循环重查 used 环；在定时器路径挂 `virtio_disk_watchdog()` 看门狗（定时器不经过外部中断链），每 tick 兜底清理积压完成项。
- **验证**：修复后 `manywrites` 通过，LoongArch 完整版 usertests首次全绿；设计权衡记录于 `docs/design.md`。

## P6. SMP 下 fat32 并发分配挂死（C1）

- **现象与取证**：新增 SMP 压测（CPUS=3、三路并发 1MiB 写入）时，fat32 段确定性挂死；ext2 对照正常。
- **根因**：fat32 分配器“读 FAT→判零→写 EOC”的读改写序列无锁，双 CPU 可同时分到同一簇；ext2 位图操作因持有缓冲块锁天然串行。
- **修复**：两个后端各加一把 sleeplock 包裹分配/释放路径；锁序规定为inode 锁 → 后端锁 → 缓冲锁（见 `lock_order.md`）。
- **验证**：修复后 SMP 测试点双架构通过；压测后 e2fsck 零错误。

## P7. fat32 大文件写入分钟级耗时（O(n²) 链漫游）

- **现象与取证**：SMP 压测中 fat32 写 1 MiB 超过 100 秒无法完成。基准测量定位：每写一块都从链头重扫 FAT 链，1 MiB 文件约需 200 万次FAT 查询。
- **根因**：`fat32_cluster_at` 无位置缓存，顺序访问退化为 O(n²)。
- **修复**：内存 inode 空槽位缓存最近漫游位置（索引→簇号），顺序访问降为 O(1)/块；缓存随 inode 填充/截断失效。
- **验证**：同负载基准对比 273→57 ticks（写）与 86→4 ticks（读）；原始数据在 `tests/evidence/bench-*.txt`。

## P8. 测试驱动的两个工程缺陷

- **现象**：长耗时命令（bigfile 约 20 秒）后的断言稳定漏判；长命令执行期间后续输入偶发丢失。
- **根因**：runner 固定步长等待，不识别“输出何时出现”；UART 控制台输入缓冲仅 128 字节，提前键入超限即被丢弃。
- **修复**：runner 增加 `--final-wait`（等齐全部 expect 再判定）与`--prompt-wait`（输出静默 + 行尾提示符双条件才发下一条）。
- **验证**：SMP 与 ext2 大文件用例在双架构稳定通过；既有套件零回归。

## P9. 基线副本缺失文件导致 diff 口径失真

- **现象与取证**：准备基线锚定文档时发现 `xv6-riscv-src/` 缺`mkfs/mkfs.c`；与官方 rev5 tag 全量比对确认其余文件一致。
- **根因**：初赛导入时目录自带的 `.gitignore` 中针对编译产物的 `mkfs`规则把同名源码目录也匹配了，文件被静默漏提交。
- **修复**：补回该文件并强制入库；与官方 rev5 tag（commit 7d7adbb）逐文件递归比对零差异。
- **验证**：diff 基线完整性确认；diff 生成命令可复现。
