# 比赛收获

本文档总结团队在本赛题中的具体收获，分技术、工程方法、协作过程三方面，最后说明现版本的不足与后续方向。文中所述内容均可在仓库代码与文档中找到对应产物。

## 技术收获

**文件系统从“读懂”到“写对”。** 赛题要求在同一内核中让三种文件系统共存，这迫使团队把 xv6 原生文件系统的调用链、inode 缓存、日志与路径解析逐行读透（精读记录见 `../notes/02-fs-chain.md`、`../notes/03-namex.md`），再依据 ext2 与 fat32 规范独立实现两个后端。这一过程中获得的不是规范条文知识，而是实现级的判断力：哪些语义必须由内核保证（如打开中的文件被 unlink 后的延迟释放），哪些可以按教学系统定位简化（如 fat32 只实现 LFN 读），每一个取舍都在 `../design.md` 的设计边界一节留了记录。

**并发正确性要靠规则而不是运气。** 决赛阶段的 SMP 压测暴露出 fat32 并发分配挂死问题，修复过程让团队建立起明确的锁规则意识：先定义锁的层级与持有顺序，再谈功能实现。这套规则被固化在 `lock_order.md` 中，成为后续所有改动的审查依据。LoongArch 平台丢失磁盘完成中断导致挂死的问题，则让团队理解到外部中断链在工程上无法保证百分之百不丢中断，稳定系统必须在机制层设计兜底——virtio 看门狗由此而来。

**跨平台移植的关键是收敛差异。** 双平台支持没有采用“复制一份内核再改”的路线，而是把平台差异逐项识别出来（启动序列、中断控制器、virtio 传输方式），收敛到独立的移植层，使文件系统与 VFS 代码在两个平台上完全共享。这一实践让团队体会到：好的抽象不是多加一层，而是让差异只出现在一个地方。

## 工程方法收获

**基线锚定与 diff 克制。** 赛题以 diff 度量改动量，团队从第一天起就建立基线副本并锚定版本（`baseline.md`），每处改动都要回答“不改行不行”。最终 diff 为 62 个文件、+6635/−119 行，其中 37 个新增文件贡献 +5829 行，25 个 rev5 既有文件为 +806/−119；这个数字不是靠最后删减得来的，而是每阶段克制的结果。

**缺陷驱动的测试建设。** 测试体系不是一次规划出来的：每修复一个缺陷，就把触发它的场景固化为一个测试点，最终形成 11 测试点 × 2 架构的回归门禁，配合证据归档（`tests/evidence/`）做到任何结论可复核。团队由此确认了一个事实：测试的价值在于缺陷出现之前已经存在，而不是之后补上。

**阶段化推进与留痕。** 项目按十八个阶段（阶段 0 至阶段 Q）推进，每阶段以“目标、改动、验证”三要素记录（`../progress.md`），并与提交历史一一对应。这种方式在决赛复盘时显出价值：任何一行 diff 都能回溯到它所属的阶段、要解决的问题和当时的验证输出。

## 协作过程收获

三人团队按子系统分工、以评审和回归门禁衔接（分工详见 `collaboration.md`）。实践中形成的共识是：分工的边界靠接口定义而不是口头约定，VFS 层接口先行的做法让文件系统与平台两条线得以并行推进；每个阶段结束时的交叉评审与全量回归，则保证了并行推进不会积累集成风险。AI 工具参与了需求分析与代码审查环节，团队形成的用法是“AI 给候选方案，人做验证与决断”，所有采纳的建议都经过人工理解与测试，这一原则写入 `ai_usage.md` 并全程执行。

## 不足与后续方向

现版本为保持教学系统的体量做了明确的取舍：fat32 后端不支持 LFN 写入、ext2 不支持日志，挂载表为静态容量。这些边界在 `../design.md` 中均有说明，对应的扩展方向也清晰：fat32 的 LFN 写路径与 ext3 式日志可在现有后端接口上增量加入，VFS 层的数据结构无需变动；HAL 目前的抽象面覆盖本赛题的两个平台，接入新平台时需要补充的中断路由知识已有 `../notes/06-hal-design-walkthrough.md` 的推导记录可循。这些未做项是主动取舍而非能力缺口，构成后续迭代的具体起点。
