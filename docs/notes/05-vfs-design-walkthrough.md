# 05 VFS 设计推导

本篇记录 VFS 层从需求到形态的推导过程，回答“为什么这样设计”。

## 需求约束

1. 同时支持 xv6/ext2/fat32，且 xv6 原生行为不能变（自带测例必须通过）；
2. 增加的代码尽量少（赛题明示）；
3. 教学可读——每个抽象都要能在课堂上讲清。

## 关键决策推导

**决策 1：在哪里接入？** 候选：改 `file.c`（文件描述符层）/改 `fs.c`（inode 层）/新建分发层。选择：在 inode 操作边界接入——`struct inode` 增加 `fstype/mnt/ops`，读/写/统计/截断/查找/创建/链接/删除八个操作经 `ops` 表分发。理由：inode 是 xv6 文件系统概念的汇聚点，在这里接入对调用方几乎透明；`file.c` 层不需要知道后端差异。

**决策 2：操作表多细？** 候选：完整对象模型（Linux 式四层）/单一 inode_ops 表 + fs_ops 挂载表。选择：后者（`vfs.c` 406 行）。理由：Linux 模型对教学过量；而只留 ops 表会丢失挂载管理能力——所以保留一个最小的 `mount` 结构与挂载表，刚好支撑挂载点跳转与 `..` 回退。

**决策 3：xv6 原生后端如何处理？** 选择：把原生文件系统注册为默认后端（`xv6_inode_ops` 指向原有函数），根挂载在 `vfsinit` 建立。理由：所有路径解析统一走 VFS，但原生路径的函数一个不改——行为不变是可证明的（diff 评审可读）。

**决策 4：挂载调用与生命周期如何协调？** 选择：拓扑修改专用的 `mtable.oplock` + 四态挂载表（NMOUNT 槽位）+ 每后端一个静态 fs 实例。可睡眠 `oplock` 串行化整次 `vfs_mount()/vfs_umount()`；短持有 `mtable.lock` 完成 `MOUNT_FREE/MOUNTING/MOUNTED/MOUNT_UNMOUNTING` 转换和 reader pin。路径只进入 `MOUNTED` 根 inode，所有非空状态都让 unlink 看见挂载点正在使用；卸载复用 `inode.ref` 判断打开文件、cwd、在途路径和子挂载。同类型后端只允许一个非空表项，与静态单实例设计一致。该组合不维护完整拓扑，“先挂 `/a/b`、再挂 `/a`”的反向祖先覆盖仍是 P1 限制。

## 推导的验证

- 三系统共存互拷（public_vfs 套件）；
- 挂载点 `..`、挂载点删除保护、重复挂载拒绝（semantics/error 套件）；
- 对 rev5 原有文件的修改约 130 行——“薄”是可度量的。
